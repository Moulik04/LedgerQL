# Phase 5.5, Task 6b(a) — Empty Result → NO_DATA Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a deterministic abstain trigger that fires `NO_DATA` when the
consensus winner's result is empty (or a single row of all-`NULL` values)
**and** the winning SQL anchors on a specific company via `cik`, `ticker`,
or `name` — closing 6 missed abstains (G03, M07, T05, T10, U04, U06)
without breaking G06, the gold case where an empty result is itself the
correct answer.

**Architecture:** A new pure module, `ledgerql/result_shape.py`, inspects
the winning SQL's already-parseable `sqlglot` AST (the same library
`guardrails.py` already uses) for an equality/`LIKE`/`ILIKE` predicate
binding an identity column to a literal, and reports whether the winning
row set is empty-or-null. `ledgerql/pipeline.py` calls it once, between the
existing `LOW_AGREEMENT` check and `write_answer()`, and short-circuits to
`reason_code="NO_DATA"` before ever generating or verifying an answer —
mirroring the existing `LOW_AGREEMENT` short-circuit's shape exactly.

**Tech Stack:** Python 3.12, `sqlglot` (already a dependency via
`guardrails.py`), pytest with `monkeypatch` — same patterns as every prior
phase.

**Spec:** [docs/superpowers/specs/2026-09-16-phase5.5-task6b-design.md](../specs/2026-09-16-phase5.5-task6b-design.md), section 1.

## Verified facts this plan depends on

Confirmed directly against the real environment before writing this plan (not assumed):

- **The six target cases' actual winning SQL** (from `reports/eval_bridges2_qwen3_30b.jsonl`, the 30B run — the exact baseline `DECISIONS.md`'s 2026-09-16 13/8 split is measured against) all contain an equality predicate on `cik`, `ticker`, or `name` against a literal, including inside a subquery (U06: `cik = (SELECT cik FROM companies WHERE ticker = 'TSLA')`). G06's SQL (`WHERE fiscal_year=2024 AND value<0`) contains no such predicate. See spec section 1c for the full table.
- **`sqlglot.parse(sql, read="duckdb")` returns a list of `exp.Expression`**, and `tree.find_all(exp.EQ, exp.Like, exp.ILike)` recurses into subqueries by default — verified directly: parsing `"SELECT fiscal_period FROM filings WHERE cik = (SELECT cik FROM companies WHERE ticker = 'TSLA') AND form = '8-K' ... LIMIT 1"` and calling `find_all` on the outer tree returns **three** `EQ` nodes, including the inner `ticker = 'TSLA'` living inside the subquery — no manual subquery-walking needed.
- **`exp.EQ`/`exp.Like`/`exp.ILike` nodes expose `.this` (left operand) and `.expression` (right operand)**, and `exp.Column` exposes a `.name` string property (verified: `next(tree.find_all(exp.Column)).name` returns `"ticker"`, a plain `str`, not an `Identifier` object — do not use `.this` on a `Column` for the name, that returns the `Identifier` wrapper). A join condition like `v.cik = c.cik` produces an `EQ` whose `.this` is a `Column` named `cik` — the identity-column check must also verify the **other side** is `exp.Literal` or `exp.Subquery`/`exp.Select`, not another `exp.Column`, or every join condition on `cik` would false-positive.
- **`sqlglot.parse()` raises `sqlglot.errors.ParseError` on malformed input** (verified: `sqlglot.parse("not valid sql (((", read="duckdb")` raises it) — the new module must not let a parse failure propagate out of the pipeline; `ledgerql/pipeline.py`'s outer `try/except Exception` catch-all would technically catch it, but that would silently mis-attribute a parse bug to `EXEC_ERROR` at the top level instead of this stage failing closed (returning `False`, i.e. "not an identity-anchored empty result, answer normally") the same way `guardrails.py`'s own parsing does.
- **Current `ledgerql/pipeline.py` (213 lines), `ledgerql/consensus.py`, `ledgerql/answer.py`, `tests/test_pipeline.py` (are all as of this plan's writing) were read in full** — the `LOW_AGREEMENT` short-circuit this plan mirrors is at `ledgerql/pipeline.py:103-115`; the `write_answer()` call this plan's new check must precede is at `ledgerql/pipeline.py:117-122`.

```python
# ledgerql/result_shape.py
"""Stage 6.5: identity-anchored empty-result detection.

Distinguishes two shapes that look identical at the row-count level but
require opposite treatment: a query anchored on one specific company
(cik/ticker/name bound to a literal) that returns nothing means that
company's data for the requested slice is absent -- NO_DATA. A query with
no such anchor (e.g. "which companies had negative total assets") is a
set/filter question where an empty result is itself a valid, complete
answer and must be left alone.

The distinction is read off the already-parsed sqlglot AST (the same
library ledgerql/guardrails.py uses for its allowlist checks) rather than
matched against any of the specific business concepts a question happens
to ask about -- see docs/superpowers/specs/2026-09-16-phase5.5-task6b-design.md
section 1c for the full rationale and the gold case (G06) this exists to
avoid breaking.
"""

from __future__ import annotations

import sqlglot
from sqlglot import exp
from sqlglot.errors import ParseError

# The three columns docs/schema.md documents as identifying a single
# company row -- present on `companies` and propagated onto every concept
# view (v_revenue, v_net_income, v_total_assets, v_cash). Fixed and small
# by schema design, not an enumerated list of business concepts -- do not
# grow this set without updating the spec.
IDENTITY_COLUMNS = {"cik", "ticker", "name"}

_LITERAL_ANCHOR_TYPES = (exp.Literal, exp.Subquery, exp.Select)


def _is_empty_or_null(rows: list[tuple]) -> bool:
    if not rows:
        return True
    return all(v is None for row in rows for v in row)


def _binds_identity_column_to_a_literal(sql: str) -> bool:
    try:
        trees = sqlglot.parse(sql, read="duckdb")
    except ParseError:
        # Fail closed: an unparseable string is guardrails.py's problem,
        # not this stage's -- treat it as "not anchored" so an empty
        # result from it is answered normally rather than mis-flagged.
        return False

    for tree in trees:
        if tree is None:
            continue
        for predicate in tree.find_all(exp.EQ, exp.Like, exp.ILike):
            left, right = predicate.this, predicate.expression
            for identity_side, other_side in ((left, right), (right, left)):
                if (
                    isinstance(identity_side, exp.Column)
                    and identity_side.name.lower() in IDENTITY_COLUMNS
                    and isinstance(other_side, _LITERAL_ANCHOR_TYPES)
                ):
                    return True
    return False


def is_identity_anchored_empty(sql: str | None, rows: list[tuple]) -> bool:
    """True if `rows` is empty or a single all-NULL row, AND `sql` binds
    `cik`, `ticker`, or `name` to a literal (directly or inside a
    subquery) somewhere in its WHERE/ON/HAVING clauses. This is the
    signal that a specific company's data is absent, as opposed to a
    set/filter query for which an empty result is itself a valid answer.
    """
    if not sql or not _is_empty_or_null(rows):
        return False
    return _binds_identity_column_to_a_literal(sql)
```
