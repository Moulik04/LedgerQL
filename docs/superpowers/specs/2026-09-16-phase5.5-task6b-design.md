## 0. Why Task 6b is four mechanisms, not one

The 21 cases in scope collapse into four structurally distinct failures.
Solving them with one mechanism (e.g. "make the classifier stricter," which
`PHASE_5_5_MASTER_PROMPT.md`'s original Task 6 tried and
`DECISIONS.md`'s 2026-09-15 "Corrected hypothesis" entry found didn't apply
to most of these cases) would either miss most of the gap or overfit to
gold's specific questions. Each sub-part below is scoped, verified, and
(for (a) only) designed independently.

| part | cases | n | mechanism needed |
|---|---|---|---|
| (a) | G03, M07, T05, T10, U04, U06 | 6 | structural: empty winning result on an identity-anchored query |
| (b) | H02, H03, H05, O07, **O02** (rescoped, §3) | 5 | schema-concept check: SQL is valid but the concept has no representation |
| (c) | O06 (O02 moved to (b), §3) | 1 | model-dependent classifier instability, not a missing few-shot |
| (d) | M03 | 1 | needs Task 2 (third output state) — out of 6b scope |

The original task list put O02 in (c) alongside O06; §3 below found that
scoping wrong (measured, not assumed) and moves it. The table above
reflects the corrected scope, not the task's original grouping.

## 1. Part (a) — empty result → NO_DATA

### 1a. Verification (done before any design)

The master prompt's hypothesis: "5 candidates return empty, cluster at
agreement 1.0, and the answer stage writes prose from an empty table."
Verified directly against the two committed Bridges-2 reports
(`reports/eval_bridges2_qwen3_30b.jsonl`, `reports/eval_bridges2_qwen25_32b.jsonl`),
replayed through `intent.check()` first (the same substitution
`DECISIONS.md`'s 2026-09-16 entry used, since that entry's 13/8 split is
itself measured against the post-intent.py state, confirmed below to
reproduce exactly on the 30B run) — **not a fresh run**, per that entry's
own "measured vs. derived" discipline.

Confirmed:
- All 6 cases have `agreement: 1.0` (or 0.6/0.6/1.0/1.0/1.0/1.0 on 32B —
  still a clear plurality winner, not a tie) and a winning result that is
  either genuinely empty (`rows: []`, 5 of 6) or a single row of `NULL`
  (T05's CAGR calc on 30B: `rows: [[None]]` — an aggregate over an
  unmatched join key, same failure shape as an empty result, not caught by
  a bare `len(rows) == 0` check).
- `write_answer()` is in fact called on this empty/null table and produces
  exactly the prose the hypothesis predicted: *"The table shows no data
  rows for the requested result."* — a fluent, confident-sounding sentence
  with nothing behind it.
- `verify.py` passes it: there are no numbers in "no data rows" to fail
  grounding, so `UNGROUNDED_ANSWER` never fires. The empty-result case is
  invisible to the existing safety layer by construction — it isn't a
  loosened tolerance, it's a case the verifier was never asked about.

**Confirmed. Do this first, as scoped.**

### 1b. The naive rule doesn't work — verified, not assumed

Simulating "any winning result with `len(rows) == 0` or all-NULL values →
NO_DATA" against both committed reports (a throwaway replay: apply
`intent.check()` to the committed per-case records, then flip any answered
record whose winner is empty/all-NULL; the script lived in a scratch
directory and did not survive a reboot, so this is described rather than
linked) shows it is **not** a safe rule as stated. It breaks a currently-**correct** case:

- **G06** ("Which companies reported negative total assets in fiscal year
  2024?") — gold: `expected: ANSWER`, `compare: empty`,
  `accept_alternatives: ["stating clearly that none matched"]`. The 30B run
  already answers this correctly (`execution_correct: True`) with "no
  companies reported negative total assets." A blind empty-result rule
  would abstain on it instead — a real regression on a case gold explicitly
  designed to test that empty-is-a-valid-answer.

It also degrades several already-wrong `ANSWER` cases (L11, L12, on 32B
also L06/R02/R05) from "wrong answer" to "false abstain" — a lateral move
for `overall_execution_accuracy` (both score 0 either way — see
`evals/run_eval.py:203-212`, `execution_correct` gates on `results_match()`,
which the flip doesn't touch) but a real, measurable cost to
`abstain_precision_decision`'s numerator being diluted by new false
abstains. See §1e for why this interacts with Task 5, not something to
paper over here.

So the fix cannot be "any empty result is NO_DATA." G03/M07/T05/T10/U04/U06
and G06 have the same observable shape (`compare: empty` in gold, empty or
null winning result at runtime) and opposite correct behavior. The
distinguishing feature has to come from somewhere else, and per the task's
own constraint it must be structural — not a keyword list of "this
question is a lookup, that one is a filter."

### 1c. The structural distinction: identity-anchored lookup vs. a set query

Inspecting the six winning SQL strings against G06's:

| case | WHERE clause shape |
|---|---|
| G03 | `name = 'Acme Rockets Inc' AND fiscal_year = 2024` |
| M07 | `ticker = 'GOOG' AND fiscal_year = 2024` |
| T10 | `ticker = 'NVDA' AND fiscal_year = 2025` |
| U04 | `ticker = 'NVDA' AND fiscal_year = 2020` |
| U06 | `cik = (SELECT cik FROM companies WHERE ticker = 'TSLA') AND form = '8-K' ... LIMIT 1` |
| T05 | `ticker = 'AAPL' AND fiscal_year IN (2022, 2025)` (aggregate, no GROUP BY) |
| **G06** | `fiscal_year = 2024 AND value < 0` — **no identity-column filter at all** |

All six target cases bind an **identity column** — `cik`, `ticker`, or
`name`, the three columns `docs/schema.md` documents as identifying a
single company row, present on `companies` and propagated onto every
concept view (`v_revenue`, `v_net_income`, `v_total_assets`, `v_cash` all
carry `cik, ticker, name` per `docs/schema.md`'s "Concept views" section)
— to a literal value via equality (`=`, `ILIKE`/`LIKE` against a literal
name, or an equality-bound subquery on `companies`). G06 does not: its
filter is `value < 0`, a comparison over a data column, with no equality
anchor on any identity column anywhere in the query. That is the
structural difference between "this specific thing's data" (empty means
absent) and "which of these things" (empty means none, and none is an
answer).

This is inspectable directly from `guardrails.py`'s already-parsed
`sqlglot` AST (`ledgerql/guardrails.py` already imports `sqlglot.exp` for
the allowlist checks) — no new dependency, and it reasons about a fixed,
already-known **schema role** (which three columns identify a company),
not an enumerated list of business concepts. It generalizes to a held-out
question the same way the allowlist check does: any new identity-anchored
question over any of these tables gets the same treatment, without a new
line of code.

**Rule:** a winning result that is empty or a single row of all-`NULL`
values is `NO_DATA` if the winning SQL's `WHERE` clause (including
subqueries) contains at least one equality-shaped predicate binding `cik`,
`ticker`, or `name` to a literal. Otherwise, the empty/null result is left
alone and answered normally, exactly as it is today (preserving G06).

### 1d. Where this sits in the pipeline

> **Revised 2026-09-18 (§1i):** it now runs *before* the agreement gate, on
> the executed candidates. The placement described here was the first design.

`ledgerql/pipeline.py`'s `ask()`, between the `LOW_AGREEMENT_THRESHOLD`
check and the `write_answer()` call (`ledgerql/pipeline.py:120-134`): once
`consensus_result.reason_code is None` and agreement clears the threshold,
check the winning result against the new rule before ever calling
`answer_module.write_answer()`. If it fires, short-circuit to
`reason_code="NO_DATA"` the same way the existing `LOW_AGREEMENT` branch
does — no LLM call for `write_answer()` or `verify()` happens at all
(measurable secondary benefit: one fewer LLM round trip per case this
rule catches).

This is new code, not a loosened check — it adds an abstain trigger, it
doesn't relax the verifier or a guardrail, so it doesn't fall under the
master prompt's "stop before loosening a tolerance" checkpoint. It is
still a safety-adjacent change to the consensus/answer boundary and gets
reviewed like one.

### 1e. Interaction with Task 5

> **Implemented 2026-09-18 (§5):** the repair pass exists and the empty-result
> trigger runs before `NO_DATA` commits.
 (repair-before-abstaining) — flag, don't resolve here

L11, L12 (and, on the 32B run, L06/R02/R05) are `ANSWER`-expected cases
whose *generated* SQL is wrong in a way that happens to produce an empty
result (already scoring 0 today) — not genuinely-absent data. Under this
rule they become `NO_DATA` false abstains instead of silent wrong answers.
Both score 0 on `overall_execution_accuracy` either way, but the false
abstain is a worse failure mode to ship silently, because it *looks* like
a correctly-functioning safety mechanism.

Task 5 (one repair attempt on failure, not yet built) is the correct place
to close this: if a repair pass re-generates and re-executes once when the
winning result is empty on an identity-anchored query, several of these
would very likely resolve to the correct non-empty answer instead of an
abstain, before this rule ever gets a chance to fire. **Sequencing note for
whoever picks up Task 5:** run the identity-anchored-empty check *before*
committing to NO_DATA, and if it would fire, try one repair pass first —
NO_DATA should be the fallback after a repair attempt fails, not the first
response to an empty result. This spec's plan builds the check as
described in §1d (fires immediately) since Task 5 doesn't exist yet;
whoever builds Task 5 should thread the repair attempt in ahead of this
check's short-circuit, not build a second, competing empty-result path.

### 1g. Overlap with the 8 mis-reasoned cases — checked, negative result

The task asked to check whether the 8 mis-reasoned cases (H04, H07, H08,
O04, O05, M04, M05, T06) overlap with (a). They do not, and the reason is
structural: all 8 fail *before* reaching a winning result at all —
H04/H07/H08/O04/T06 hit consensus's no-usable-cluster branch
(`ledgerql/consensus.py`'s `if not clusters:` path, `reason_code:
EXEC_ERROR` or, where a guardrail named something, that name) because no
candidate executed successfully across all 5 samples; O05/M04/M05 hit
`LOW_AGREEMENT` because candidates disagreed too much to cluster. Neither
path ever calls `write_answer()`, so there is no winning empty result for
this rule to inspect — `result.answer is None` and `result.rows == []`
before this check would ever run. Confirmed by replaying all 8 through the
real shipped `is_identity_anchored_empty()`, on the 30B run (the baseline
this 13/8 split is measured against): none of the 8 are even eligible —
none reached a winning result at all, let alone an empty one. **The master
prompt's "if they do overlap, (a) fixes more than 6 cases" is answered:
on the baseline run, they don't, and (a) fixes exactly 6 target cases plus
a partial (wrong-reason) assist on 1 of (b)'s 4** (H02 — see §1f).

One secondary data point, not part of the baseline claim above: on the
32B run (a different configuration, not the one the 13/8 split is
measured against), **T06** does reach a winning empty result
(`WHERE ticker = 'AAPL' AND fiscal_year = 2025 AND fiscal_period = 'Q2'`,
empty rows, answered) and does get flagged. This isn't evidence against
the "no overlap" finding for the actual baseline — it shows the mechanism
generalizes to at least one case outside its original target list on a
different model, which is the intended behavior of a structural rule
rather than a memorized one.

Hallucinated-number rate: **0.0% of 44 answered cases.** Abstain metrics on

### 1i. Gate ordering: unanimity among survivors, before the agreement gate (2026-09-18)

`LOW_AGREEMENT` divides by N (5), not by the candidates that executed, so one
survivor among four errored candidates scores 0.2 and hides that everything
that ran was unanimously empty. The predicate is now `survivors_unanimously_empty
and is_entity_bound(winner_sql)` and is evaluated first. Empty survivors list
is *not* an empty-result signal (`all([])` is `True`; guarded and tested) — it
is consensus's `EXEC_ERROR` path.

Effects, checked rather than assumed:
- Recorded agreement for the six targets is 1.0 on 30B for all six, so the
  replay was not overstated on the 30B baseline. T05 on 32B is 0.6, so the
  32B figures are now a range.
- ~~The reorder changes only the reason code of records that already abstain;
  it cannot move a decision metric.~~ **Wrong as built, corrected 2026-09-20.**
  Moving the check before the gate does only change reason codes. But the
  same change also made the predicate *stricter* (every survivor empty, not
  just the winner), and that does move decisions: on the 7B, M07 and M04
  (winner empty and entity-bound at agreement 0.8, one dissenting survivor)
  stopped being caught and were answered from an empty table, taking missed
  abstains from 2 to 4 and decision recall from 94.1% to 88.2%. The replay's
  "lower bound" was modelling exactly this. The fix is a union, not a
  replacement: unanimity among survivors catches what the gate masks, and a
  winner that is empty *and* clears the gate is caught as before
  (`pipeline._no_data_signal`). Below the gate with a dissent the honest
  reason is `LOW_AGREEMENT`.
- It does **not** reach T05 on the 7B (winner `[[None], [2.0975…]]`, a bogus
  two-row CAGR — not empty). It reaches U06.
- The committed records hold only the winner's agreement, so survivor
  unanimity cannot be confirmed at agreement < 1.0. The replay is reported as
  an upper bound (every winner-empty entity-bound flip) and a lower bound
  (agreement 1.0 only).

### 1j. Where the rule stops being principled

See DECISIONS.md, 2026-09-18, item 3. In short: entity-bound + empty
approximates presupposition failure and is not identical to it. An
entity-bound list/existence query whose true answer is "none" would
false-abstain; gold has none. A scalar-shape refinement would separate them
and is deliberately not built (no gold case would exercise it; adding one
needs MJ's sign-off). The rule also cannot tell a real absence from a wrong
literal. A repair for that was tried and cut (2026-09-20: an empty result carries no error to feed back), so a wrong-literal query is an accepted false abstain (L12).

## 2. Part (b) — schema-concept check (reduced, 2026-09-18)

**Verify first, as directed.** H03 and O07 emit `SELECT NULL AS credit_rating
WHERE 1 = 0` and `SELECT NULL AS customer_satisfaction_score WHERE FALSE` —
the generator refusing in SQL. The AST shows a constant-false `WHERE`
(`EQ(Literal 1, Literal 0)`, `Boolean(False)`), no `FROM`, and an all-`NULL`
projection. H02 and H05 have none of these.

**Built:** `result_shape.is_tautologically_empty(sql)`: a constant-false
`WHERE` (Boolean false, NULL, a comparison of two literals that evaluates
false, `NOT TRUE`, `AND` with a false operand, `OR` of all-false operands), or
a no-`FROM` query whose every projection is `NULL`. Mixed-type comparisons
(`1 = 'a'`) are undecidable and not flagged. The pipeline maps a winner that
is tautologically empty, with unanimously empty survivors, to
`SCHEMA_MISMATCH` before any repair — a repair would push the model to
invent the thing it just declined to invent. No concept list; it holds for
any concept a held-out question asks about. Verified by mutation: disabling
the check fails the pipeline tests.

Measured on the committed 30B records: it fires on exactly H03 and O07 and
nothing else; 0 hits on 32B (different generations, no such SQL).

**What remains of (b):**
- **H02** — entity-bound and empty, so it is repaired and then `NO_DATA`;
  gold wants `SCHEMA_MISMATCH` (decision-correct, reason wrong). Nothing
  structural separates "TSLA's `EmployeeCount` is absent" from "TSLA's revenue
  for that year is absent" except that the tag is not in the mart's documented
  scope; that needs a tag-vocabulary check, not built.
- **H05** — `COUNT(*)` returning a real `0`, not empty; open.
- **O02** — 30B emits `SELECT 'Tim Cook' AS ceo_name WHERE EXISTS(...)`, a
  string constant from model memory with no column reference. The numeric
  verifier cannot see a string fact. A "projection with no column references"
  check is the structural next step; recorded, not built.

## 3. Part (c) — classifier reliability on O02/O06

### 3a. First-pass diagnosis (measured, not assumed) — the two cases are not the same kind of failure

Called `ledgerql.classify.classify()` directly, live, against the real
local `qwen2.5-coder:7b` (3 seeds each: 42, 1, 7):

| question | verdict, all 3 seeds |
|---|---|
| "Write a short poem about Microsoft's balance sheet." (O06) | **OUT_OF_SCOPE**, 3/3 |
| "Who is the CEO of Apple?" (O02) | **IN_SCOPE**, 3/3 |

**O06 does not reproduce as a classifier failure on this model, right
now.** It classifies correctly, consistently, exactly matching the
near-identical few-shot example already in `_FEW_SHOT`
(`ledgerql/classify.py:138`, `"Write a short poem about Microsoft." ->
OUT_OF_SCOPE`). But the committed reports show it failing on **30B**
(`reports/eval_bridges2_qwen3_30b.jsonl`: O06 was answered, i.e.
classified `IN_SCOPE` there) while correctly refusing on **32B**
(`OUT_OF_SCOPE`). This is the same shape of failure `DECISIONS.md`'s
2026-09-15 entry found for S01-S06 before `ledgerql/intent.py` existed:
*not stable across models*, which is a real reliability problem, but a
different one than "the few-shot example doesn't work" — it works on two
of the three models tested and fails on the third. Whether creative-intent
detection can be made a deterministic, model-independent Stage-0 check the
way destructive-SQL-intent was (`intent.py`), or whether this specific
instability needs a different fix, is exactly the kind of question
`superpowers:systematic-debugging` should drive — not started here, but
now scoped with a concrete, reproduced discrepancy to debug rather than an
assumed one.

**O02 is not a classifier reliability problem at all — it's a
mis-scoped instance of (b).** `classify.py`'s own docstring (design
correction #3, `ledgerql/classify.py:59-90`) documents that this layer
was *deliberately* changed to let "a plausible-sounding fact the database
doesn't have" (its own examples: market capitalization, customer
satisfaction rating) pass through as `IN_SCOPE`, precisely so a downstream,
more precise layer can give the real reason. "Who is the CEO of Apple?" is
exactly that shape — a plausible company fact ("CEO") the mart has no
representation for at all, structurally identical to O04's share-price gap
and H02/H03/H05/O07's tag gaps. `classify.py` returning `IN_SCOPE` here is
the code doing exactly what its own design history says it should do, not
a bug. Routing O02 into "strengthen the classifier" would repeat the
Task 6 mistake `DECISIONS.md`'s 2026-09-15 entry already documented once
(building a fix for a hypothesized failure without checking whether that
layer is actually where the case fails) — a second instance of that same
mistake, this time inside the very task (Task 6b) that split off from the
first one to avoid it.

**Revised scope:** O02 moves to part (b) (a schema-concept check that
catches "CEO," "market capitalization," "customer satisfaction score," and
similar untracked concepts uniformly, not four separate special cases).
O06 stays in (c), rescoped from "add few-shots" to "diagnose the
model-dependent instability of creative-intent detection, and decide
whether it needs a deterministic Stage-0 check the way destructive intent
did" — a `superpowers:systematic-debugging` pass, not started here.

## 5. Task 5 repair pass (2026-09-18)

`ledgerql/repair.py`, `generate.repair_candidate`, the shared tail in
`pipeline.py`. One attempt, no loop.

| trigger | fires when |
|---|---|
| `exec_error` | no usable cluster, reason `EXEC_ERROR` |
| `schema_mismatch` | no usable cluster, reason `SCHEMA_MISMATCH`, no stray table. **Built, tested, disabled** (`repair.ENABLED_TRIGGERS`) for the Bridges-2 batch |
| ~~`empty_entity_bound`~~ | **cut 2026-09-20**: an empty result carries no error to feed back; rejected design, see DECISIONS.md |

**Flow.** Repaired SQL -> `guardrails.validate` -> `execute` -> for the empty
trigger it must be non-empty -> if it lands empty and entity-bound anyway,
`NO_DATA` (the cap: no second repair) -> otherwise `write_answer` -> `verify`.
Any failure abstains with the original reason and the attempt recorded. A
repair that hands back the same SQL (normalised for case, whitespace, trailing
semicolon) repaired nothing.

**Carve-out.** A stray *table* is never repaired (`information_schema`, a
staging table). `guardrails.py` returns `SCHEMA_MISMATCH` for both a stray
table and a stray column; S07 and S11 are correct refusals on that same path,
and repairing them would rewrite a schema-snooping request into an allowed
query and answer it. The split is re-derived from the AST with
`guardrails.check_table_allowlist`, not from the detail string. This deviates
from Task 5 as written and is flagged to MJ.

**Empty-result prompt** does not say "make this return rows" (that loosens
filters until something comes back, turning a correct `NO_DATA` into a
fabricated answer). It offers "specific mistake" vs "genuinely absent" and
says to return the query unchanged in the latter case.

**Confidence.** A repaired result has no self-consistency signal; confidence
is `None`, not an invented agreement. Task 1's model must treat `repaired` as
its own regime.

**Scoring** (`evals/repair_scoring.py`, report section `## Repair`), split by
trigger: attempted; *rescued* (abstain -> answer); *rescued correct*
(matches gold where answering is right); *rescued but should have abstained*
(a required refusal converted into an answer — the harm, never netted
against wins). A residual risk remains on the stray-*column* path: a correct
concept-gap refusal (an invented `dividend_yield`) may be repaired into a
wrong answer; the harm column exists to expose it.

**Not replayable.** Repair needs generation. Derived 30B/32B figures assume it
leaves the six `NO_DATA` targets alone.
